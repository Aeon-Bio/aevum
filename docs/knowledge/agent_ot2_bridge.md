# Agent OT-2 Bridge

## Design Target

LLM agents should be able to reason about OT-2 work, propose plans, and request
robot actions without receiving raw, concurrent control over physical motion.
The package should provide a stateful bridge core that owns the robot
connection, safety checks, sessions, serialization, offsets, and evidence.

```text
LLM agents
  -> small agent adapter surface
    -> bridge session service
      -> plan validator
        -> robot lock and state store
          -> Opentrons HTTP API
            -> OT-2
```

For live robot control, a single local bridge daemon should own the robot
session. Agents and operator/debug tools are clients.

MCP, local HTTP, and CLI entry points are adapters. They are not the control
architecture. The control architecture is the bridge core plus its session,
lock, validation, registry, and evidence state.

## Operating Mode

Aevum's target operating mode is unattended autonomy for validated workflows.
The bridge should be designed so human approval is not part of the normal run
loop once a workflow, fixture, target class, and recovery path are proven.

The first printed fixture should run in supervised commissioning mode only until
machine evidence gates are validated. In commissioning, a human may confirm or
override derived claims from camera captures, physical measurements, robot
state, and command history. In unattended operation, the bridge should use
structured evidence, claims, thresholds, and recovery rules without requiring
human approval.

The OT-2 built-in camera is the first machine perception source, but it is not
the evidence model. Camera captures, caliper measurements, robot status,
command history, generated checksums, and human commissioning notes all feed the
same evidence -> claim -> gate pipeline.

## Bypass Surfaces

The bridge cannot be considered safe if other control paths remain casually
usable. Treat these as bypass surfaces:

- direct execution of `opentrons/test_p300_poc.py`,
- direct HTTP calls to the robot server,
- Jupyter Notebook control,
- `opentrons_execute`,
- the Opentrons App.

During bridge development, direct protocol files are reference scaffolds and
debug fallbacks only. A direct protocol run must either be generated by the
bridge with explicit offsets and evidence IDs, or be marked as a manual override
in the measurement record. It is not part of normal agent operation.

## Control Authority

The bridge lock is authoritative only for cooperating clients. The OT-2 robot
server is a network service, so a local SQLite lock cannot physically prevent a
different machine, the Opentrons App, Jupyter, or direct HTTP calls from
commanding the robot.

Initial deployment should state this honestly:

- guaranteed single-writer among bridge clients,
- foreign-command detection and fail-closed recovery when possible,
- operational controls to avoid bypass use during live sessions.

Stronger single-writer enforcement requires network-level control, such as
running the bridge as the only allowed route to the robot server on the lab
network. Until then, "single writer" means "single writer through the Aevum
bridge," not "single writer over the entire LAN."

## Current Decision

Use the Opentrons HTTP API as the bridge transport. Use Python Protocol API
concepts as the package's semantic model for labware, wells, pipettes, and
repeatable protocol generation. Keep agent-facing adapters coarse and
state-oriented so agents ask for validated workflow progress rather than raw
robot actions.

This keeps the robot interaction remote and inspectable while preserving the
labware/pipette abstractions that Opentrons already defines.

## Non-Negotiable Properties

- Single-writer access through Aevum bridge clients. Only one active bridge
  session may own the motion lease.
- No arbitrary Python execution from agents.
- No raw coordinate moves unless they pass a fixture-aware safety envelope.
- Every physical command records request, validation result, response, and run
  ID.
- Offsets are scoped to robot serial, labware definition, slot, pipette, and
  date.
- Dry verification is required before liquid handling.
- High-Z approach is required before low-Z approach.
- Machine evidence is the preferred source for claims; human observation is a
  supervised commissioning fallback until machine gates are validated.
- Ambiguous command state is fail-closed. If the bridge cannot prove whether a
  movement command completed, it must stop issuing motion commands and require
  recovery.
- Evidence write failure is fail-closed for physical motion.

## Bridge Responsibilities

### Session Model

All agent-facing work should happen inside a bridge session. A session is a
stateful workflow owned by the bridge, not by an agent prompt. It should carry:

- session ID,
- session kind, such as `registration`, `dry_run`, or `recovery`,
- robot identity and API version,
- fixture identity and artifact checksums,
- active lock lease,
- active run ID or maintenance run ID,
- current bridge state,
- allowed next operations,
- blocked operations with reasons,
- required evidence claims and gates,
- evidence handles,
- evidence file paths.

Agents should receive compact session context packs and opaque handles. They
should not be responsible for reconstructing robot state from raw command logs.

### Adapter Boundary

Adapters expose bridge sessions to different clients:

- MCP adapter for LLM agents,
- local HTTP adapter for programmatic control or future UI,
- CLI adapter for smoke tests, operator recovery, and development.

For live motion, adapters should call the single local bridge daemon. They should
not each instantiate independent in-process bridge state. Read-only development
commands may call core functions directly, but any command that can affect robot
state goes through the daemon.

No adapter should talk directly to the Opentrons HTTP API or implement its own
motion policy.

The agent adapter surface should be deliberately small:

```text
ot2_status()
ot2_fixture_check()
ot2_start_session(kind)
ot2_get_session_context(session_id)
ot2_validate_plan(session_id, plan)
ot2_execute_next(session_id, approved_step_id)
ot2_capture_evidence(session_id, source, target)
ot2_record_evidence(session_id, evidence)
ot2_evaluate_gates(session_id)
ot2_abort_or_recover(session_id)
ot2_close_session(session_id)
```

Do not expose low-level tools like `move_to_coordinates`, `post_command`, or
`set_offset` to agents. Those operations are internal implementation details of
validated session transitions.

Second-client behavior should be deterministic. If a session owns the live
robot lease, another client that tries to start a motion-capable session receives
`robot_busy` with the owning session ID, owner agent ID when known, state, and a
retry-after hint. Read-only status and artifact checks may proceed without the
motion lease.

### Robot Discovery

The bridge should expose a `status` operation that reads robot health and core
state:

- robot reachable at `http://<robot-ip>:31950`,
- robot server healthy,
- motor controller ready,
- robot serial,
- software/API version,
- attached pipettes and mounts,
- camera availability if exposed by the robot API or protocol path,
- deck and run state if exposed.

No motion command should run until discovery passes.

### Schema Awareness

At startup, the bridge should fetch the robot's OpenAPI description from the
robot server and pin the observed API version in logs. Generated client types are
helpful later, but the first implementation can use a narrow handwritten HTTP
client for the endpoints we actually need.

Do not use `Opentrons-Version: *` for motion commands in production bridge code.
Use discovery to learn the robot's API, then issue commands against an explicitly
tested version. If the robot server version changes outside the tested range,
the bridge should allow read-only status checks and reject motion.

The bridge should re-check robot server/API identity before every physical
command and on session resume. Startup discovery alone is not enough for
long-lived sessions.

### Lock Semantics

The single-writer-among-bridge-clients rule needs a concrete lock, not just a
convention. The first implementation should use SQLite for lock/session state
because adapters and recovery tools may be separate processes.

The lock record should include:

- robot host/IP,
- robot serial when known,
- bridge process ID,
- session ID,
- owner agent ID,
- active run ID or maintenance run ID,
- lease start time,
- lease expiry,
- last successful command ID,
- last observed robot state.

The lock should be renewed before every physical command. Lease expiry should
not automatically transfer robot control if there is an active run, active
maintenance run, or ambiguous command state. A stale lease moves the session to
`needs_recovery`; it does not hand the robot to the next agent.

If the bridge process crashes, a restarted bridge may clear the lease only after
reading robot health, active runs, command history, and the local evidence
record. If robot state and local state disagree, enter the recovery workflow
rather than handing the robot to the next agent.

### Run Modes

The bridge should implement two run modes.

`maintenance` mode:

- direct physical validation,
- small command increments,
- immediate command result polling,
- explicit stop/delete behavior,
- used for the first printed fixture and registration workflow.

`protocol` mode:

- repeatable dry or liquid workflows,
- uploaded/generated Python protocols or HTTP protocol commands,
- run analysis before execution where available,
- labware offsets attached to the run,
- command history retained under one run ID.

Only `maintenance` mode is in scope for the first implementation. `protocol`
mode is a future design target after registration, offsets, and dry motion are
proven.

### Command Keys, Reconciliation, And Retries

Physical movement commands must not be retried blindly. A timeout after `POST`
can mean any of these:

- the command was never accepted,
- the command was accepted and is queued,
- the command is running,
- the command completed but the response was lost,
- the command failed after partial motion.

The Opentrons HTTP command schema includes a `key` field for commands, but Aevum
should treat it as a correlation key unless live testing proves stronger
idempotency semantics. On timeout, the bridge should poll the run's command list
for that key and reconcile state. If reconciliation fails, the bridge must mark
the run ambiguous, stop issuing motion, and require recovery.

Bench result on 2026-05-02: maintenance-run `comment` commands accepted duplicate
keys in the same run. Two commands with the same key both returned `succeeded`
with distinct command IDs. Therefore, key lookup is not enough for
reconciliation. The bridge must compare command ID, index, status, timestamps,
command type, and params before deciding whether a command was accepted or
completed.

For movement during registration, use short absolute target moves rather than
unbounded relative jog chains where possible. Duplicate relative jogs are harder
to detect and recover from.

### Plan Validation

Agents should submit structured plans, not Python. A first plan schema can be
small:

```json
{
  "mode": "maintenance",
  "fixture": "aevum_p300_poc_fixture",
  "slot": "1",
  "pipette": "p300_single_gen2",
  "mount": "left",
  "steps": [
    {"op": "home"},
    {"op": "move_to_well", "well": "A1", "z_from_top": 20.0},
    {"op": "move_to_well", "well": "A1", "z_from_top": 10.0}
  ]
}
```

The validator should reject:

- unknown operations,
- nonmatching fixture/labware versions,
- missing offsets for low-Z motion,
- moves outside known fixture bounds,
- low-Z moves before high-Z confirmation,
- liquid actions before dry verification,
- commands from more than one active agent/session.

Plan validation should produce a machine-readable rejection reason that is
stored with the plan. Failed validation is evidence too; it helps identify agent
failure modes before they become robot motion.

### Coordinate Policy

Prefer named labware targets over raw coordinates. Raw deck coordinates should
exist only for registration, jogging, and carefully bounded diagnostics.

For the first fixture:

- derive well centers from `cad/p300_poc_fixture.params.json`,
- apply generated labware definition coordinates,
- apply a measured labware offset,
- then apply explicit test offsets for columns 1-4.

The fixture has printed guide-hole offsets by column:

```text
column 1: center
column 2: +1.0 mm X
column 3: +1.5 mm X
column 4: +2.0 mm X
```

The bridge should encode these as named test targets rather than making agents
invent offsets.

### Evidence, Claims, And Gates

The bridge should treat evidence as a first-class substrate. Camera capture is
one evidence source, alongside physical measurements, generated artifact
checksums, robot health, pipette state, command responses, command history,
offset records, and supervised commissioning notes.

The durable model is:

```text
evidence source -> evidence packet -> derived claim -> gate decision -> record/readiness state
```

Evidence packets should be immutable, indexed, and referenced by handles. Claims
should be machine-readable assertions derived from evidence, such as
`fixture_dimensions_within_tolerance`, `fixture_visible_in_slot`,
`load_labware_succeeded`, `high_z_target_centered`, or
`command_history_reconciled`. Gates should consume claims plus session state and
return pass/fail, missing claims, and blocking reasons.

Agents should receive gate state, missing claims, allowed operations, blocked
operations, and evidence handles. They should not infer readiness from raw
images, command logs, or free-text notes.

### Camera As Evidence Source

The bridge should still treat camera capture as an important operation. Camera
evidence should be attached to sessions, validation results, target-class
verification, and recovery records through generic evidence handles.

Initial camera responsibilities:

- confirm image capture works on the installed robot software,
- capture fixture-installed deck images,
- capture high-Z target approach images,
- detect printed fiducials or guide-hole regions where possible,
- estimate tip/target alignment confidence where possible,
- record image settings, path, timestamp, and command/run IDs,
- contribute claims that block autonomous promotion when confidence is below
  threshold.

Human observation may be used during supervised commissioning to label evidence,
validate thresholds, or resolve ambiguous gate results. It should not be modeled
as the desired steady-state control path.

### Safety Envelope

The bridge should maintain a fixture-specific safety profile:

- fixture slot,
- CAD-derived fixture X/Y/Z dimensions,
- measured fixture X/Y/Z dimensions from print QC,
- generated labware definition checksum,
- fixture parameter file checksum,
- conservative clearance Z,
- lowest allowed dry Z until registration is complete,
- lowest allowed wet Z after dry verification,
- max step size for registration jogging,
- max movement speed if exposed by the command surface,
- forbidden zones if future optical hardware occupies the inverted bay.

For the first `p300_poc_fixture`, start with high clearance and approach in
stages. The OT-2 does not provide bottom-contact sensing that would make a bad Z
safe. Collision avoidance must come from conservative geometry and observed
registration.

The generated labware definition is not a full collision model. It exposes wells
and dimensions; it does not encode every rail, post, guide plate, or future
optical forbidden zone. The bridge safety profile must therefore be generated
from fixture parameters/CAD metadata, not only from labware JSON.

Measured print QC must feed the runtime safety envelope. If measured bounds are
larger or less favorable than CAD-derived bounds, the bridge should use the
more conservative measured values. If measurements are missing, the bridge
should reject low-Z motion.

### Offset Workflow

The agent-native registration loop should be:

1. Confirm robot, pipette, fixture definition, and deck slot.
2. Confirm camera/image-capture path for this robot software.
3. Capture fixture-installed deck image and evaluate fixture presence/QC gates.
4. Home the robot.
5. Move to nominal A1 at a conservative high Z.
6. Capture high-Z A1 image and evaluate tip/target alignment.
7. Jog X/Y in small bounded increments only when image evidence or supervised
   commissioning observation shows the correction direction.
8. Jog Z only after X/Y centering and physical clearance are confirmed by the
   active evidence mode.
9. Save the measured offset with robot serial, slot, fixture definition, pipette,
   run ID, timestamp, and notes.
10. Require a second confirmation image before applying that offset to low-Z
   plans.

Offsets should be written to measurement records first. Code-level defaults can
be promoted only after repeated evidence.

### Structured Offset Registry

Markdown measurement notes are not enough for bridge decisions. The bridge
should maintain a structured offset registry, with Markdown as the human-readable
companion record.

Minimum registry fields:

```json
{
  "schema_version": 1,
  "created_at": "2026-05-02T00:00:00-07:00",
  "robot_serial": "unknown",
  "robot_server_version": "unknown",
  "opentrons_api_version": "unknown",
  "fixture_load_name": "aevum_p300_poc_fixture",
  "fixture_definition_uri": "aevum/aevum_p300_poc_fixture/1",
  "fixture_params_sha256": "unknown",
  "labware_definition_sha256": "unknown",
  "slot": "1",
  "pipette_name": "p300_single_gen2",
  "pipette_mount": "left",
  "tiprack_load_name": "opentrons_96_tiprack_300ul",
  "offset_mm": {"x": 0.0, "y": 0.0, "z": 0.0},
  "verification_targets": [],
  "evidence_file": "data/measurements/YYYY-MM-DD_first_fixture_ot2_run.md",
  "run_id": "unknown"
}
```

The bridge should reject low-Z motion unless a matching registry entry exists
and the requested fixture target class is present in `verification_targets`.
Center high-Z verification does not authorize off-axis low-Z motion.

### Physical Fixture QC

`fixture_check` must include the real printed part, not just generated files.
Before registration, record:

- measured X/Y/Z bounds,
- whether the base sits flat in the OT-2 deck slot,
- guide-hole openness,
- mock-well deformation,
- support/stringing cleanup state,
- obvious cracks, warping, or lifted corners.

If physical QC fails, the bridge should allow status and documentation commands
only. It should not proceed to registration.

QC should be evaluated against machine-readable thresholds, not free-text notes.
The initial thresholds are documented in
`docs/engineering/fixture_qc_acceptance.md`.

### Stop And Recovery

Maintenance-run commands are not a dependable pause mechanism once a movement is
accepted. The first fixture workflow should therefore use:

- camera snapshot before and after safety-critical transitions,
- small move segments,
- high-Z approach before low-Z approach,
- no long low-Z traverses,
- no automatic retry on motion commands,
- an emergency/stop procedure recorded in the run notes.

After any stop, timeout, crash, or ambiguous command result, assume the bridge's
internal pose model is stale. Recovery begins with evidence packets from camera
capture, command history, robot state, and local records, followed by a
conservative home or retreat only when physically safe. If evidence is
unavailable or ambiguous, unresolved recovery may require human intervention.

Recovery is a first-class workflow, not an informal instruction. The recovery
runbook lives in `docs/protocols/ot2_bridge_recovery.md` and should be exposed
through `ot2_abort_or_recover(session_id)`.

### Evidence And Audit Trail

Every robot interaction should produce an evidence bundle:

- plan JSON,
- validation result,
- robot health snapshot,
- physical measurements and inspection claims,
- run ID or maintenance run ID,
- command IDs,
- command responses/errors,
- command-history reconciliation claims,
- applied labware offsets,
- generated labware definition checksum,
- camera image paths and image-analysis results,
- operator/agent notes,
- optional human commissioning notes.

Evidence belongs under `data/measurements/` for physical runs and under
`outputs/` for generated artifacts.

Evidence must also have a structured index. Domain records should reference
evidence handles and derived claims rather than embedding large payloads. If
the bridge cannot write the evidence event and update the index synchronously
before a physical command, it should reject the command. This prevents
unaudited motion at the cost of fail-closed interruptions when local storage is
unavailable.

## Suggested Package Shape

```text
src/aevum_ot2/
  __init__.py
  core/
    __init__.py
    client.py       # narrow HTTP client for robot server
    discovery.py    # robot URL/env/mDNS resolution
    models.py       # typed plans, sessions, status, offsets, evidence
    artifacts.py    # generated params/labware checksums and identity
    registry.py     # structured offset registry
    records.py      # fixture QC and target-class commissioning records
    readiness.py    # local no-motion readiness join
    context.py      # compact session context packs for adapters/agents
    plans.py        # typed operation/plan fragments
    validation.py   # local allow/block validation
    execution.py    # typed next-step execution results
    recovery.py     # no-motion stale/failed session reconciliation
    lock.py         # single-writer lease and recovery state
    sessions.py     # persisted no-motion session lifecycle
    maintenance.py  # maintenance-run helpers and no-motion probes
    safety.py       # fixture-aware validation and envelopes
    vision.py       # camera evidence parsing and confidence gates
    evidence.py     # evidence packets, claims, gate inputs, and writers
    bridge.py       # orchestration state machine
  server/
    __init__.py
    service.py      # workflow-level service API over bridge core
    app.py          # local daemon transport
    client.py       # typed local daemon client for adapters
  adapters/
    __init__.py
    mcp.py          # coarse agent tools
    http.py         # optional programmatic API
    cli.py          # thin operator/debug wrapper
```

Keep `aevum_cad` focused on geometry and generated labware. Put robot transport
and agent-facing control in a separate `aevum_ot2` package to avoid mixing CAD
generation with live hardware control. Keep adapter code thin; the bridge core
owns all safety, session, offset, and evidence decisions.

The current implementation has no-motion session persistence, local record
helpers, and a read-only readiness join in `aevum_ot2.core`. The future daemon
should wrap those core primitives; it should not fork a second session model.

The first implemented vision layer is evidence-only. It can decide whether an
image is usable evidence, but it must not authorize live motion until
fixture/fiducial detection and target-specific thresholds are calibrated.

The first maintenance-run lifecycle spike showed that this robot-server can
create, inspect, and delete an idle maintenance run without enqueuing commands.
It also showed `GET /maintenance_runs` is not available, so crash recovery must
persist the active maintenance-run ID locally and reconcile that exact ID.

The first custom-labware no-motion spike showed that maintenance runs must
upload `outputs/labware/aevum_p300_poc_fixture.json` through
`/maintenance_runs/{runId}/labware_definitions` before `loadLabware` can
reference `aevum/aevum_p300_poc_fixture/1`. Direct reference before upload
failed with labware-definition-not-found. After upload, `loadLabware` succeeded
in slot `1` and returned loaded labware ID `aevum-fixture-post-upload`.

## First Implementation Scope

Implementation follows the dependency graph in
`docs/engineering/task_graph.md`. No-motion API engineering, physical fixture
commissioning, motion commissioning, and wet workflow work are separate lanes.

For the first printed fixture, the implemented or immediate no-motion scope is:

1. `status`: health, serial, API version, pipettes.
2. `evidence_check`: confirm evidence indexing for robot state, generated
   artifact identity, physical measurements, and camera captures.
3. `camera_check`: confirm capture path and image retrieval as one evidence
   source.
4. `fixture_check`: generated artifact checksums plus physical print QC and
   fixture-presence evidence claims.
5. `vision_check`: analyze camera evidence quality and keep motion blocked until
   calibrated fixture detectors exist.
6. `start_session`: create a registration session and lock lease without motion.
7. `records`: write fixture QC and target-class scaffold records.
8. `readiness-check`: join active no-motion session state with record handles.
9. `session-context`: return compact local state and blocked operations.
10. `plan validation`: reject motion, low-Z, wet, and unscaffolded steps unless
   explicit future gates are satisfied.
11. `recovery`: reconcile stale/failed no-motion sessions before daemon work.
12. `daemon API`: expose local workflow operations without raw OT-2 endpoints.
13. `execute-next`: validate first, then run only local/no-motion operations in
    the current daemon boundary.
14. `daemon client`: give future MCP/CLI adapters a shared typed transport.
15. `fixture-qc-scaffold`: write a fixture QC record from measured bounds and
    explicit evidence gates.
16. `target-scaffold`: write blocked target-class records from a fresh session.
17. `evidence`: write evidence packets, claims, and run records to
    `data/measurements/`.

Next implementation should either wait for post-print evidence or implement the
generic evidence packet/claim/gate model. Motion-capable adapters should wait
until that model and the motion backend exist behind `execute-next`.

First live-motion scope:

1. create a maintenance run inside a registration session,
2. home,
3. move to high-Z A1,
4. capture high-Z target evidence, with camera as the first evidence source,
5. save a structured offset only after image-based or commissioning
   confirmation.

Liquid handling and unattended protocol generation should wait until dry motion,
camera gates, recovery behavior, and offset evidence are stable.

  all stay thin?
- How should lab-network routing prevent direct writes to the robot server
  during bridge-owned sessions?
- Can named labware target moves be represented safely in maintenance mode after
  run-local custom labware upload, or should first registration still use
  bounded raw deck coordinates?

The robot-server version, camera still path, maintenance-run lifecycle behavior,
and no-motion command-key behavior have initial 2026-05-02 bench records. They
must still be re-read at session start before motion. See
