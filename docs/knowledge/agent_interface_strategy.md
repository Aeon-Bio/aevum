# Agent Interface Strategy

## Decision

Aevum should optimize around a bridge core and session model, not around MCP,
CLI, or any other adapter. MCP is likely useful for LLM agents, but only as a
thin adapter over the bridge core.

The live-motion package boundary should be:

```text
agent or operator/debug client
  -> adapter
    -> local bridge daemon
      -> bridge session core
      -> validator, lock, registry, evidence
        -> narrow Opentrons HTTP client
```

## Why Not MCP First

MCP is a good way to expose typed tools to agents, but it is not a good place to
hold hardware state. If the MCP surface mirrors the OT-2 HTTP API, agents will
need too much context and will become responsible for sequencing, offsets,
retry/recovery, and safety decisions.

That boundary is wrong for hardware. The bridge core should own state and expose
workflow-level operations.

## Desired Agent Surface

The agent tool surface should be small and coarse:

```text
ot2_status()
ot2_camera_check()
ot2_fixture_check()
ot2_start_session(kind)
ot2_get_session_context(session_id)
ot2_validate_plan(session_id, plan)
ot2_execute_next(session_id, approved_step_id)
ot2_capture_evidence(session_id, source, target)
ot2_record_evidence(session_id, evidence)
ot2_evaluate_gates(session_id)
ot2_abort_or_recover(session_id)
ot2_close_session(session_id)
```

The agent should never receive direct tools for:

- raw coordinate movement,
- arbitrary HTTP commands,
- arbitrary Python execution,
- setting offsets directly,
- deleting runs without a recovery state,
- bypassing fixture QC.
- promoting a target class without required evidence-derived claims.

## Context Packs

Agent context should be generated by the bridge as a compact state summary:

```json
{
  "session_id": "reg-2026-05-02-001",
  "kind": "registration",
  "robot": {
    "reachable": true,
    "serial": "unknown",
    "api_version": "tested-version-here"
  },
  "fixture": {
    "load_name": "aevum_p300_poc_fixture",
    "slot": "1",
    "params_sha256": "unknown",
    "labware_definition_sha256": "unknown"
  },
  "pipette": "p300_single_gen2:left",
  "state": "awaiting_high_z_a1_confirmation",
  "allowed_next_ops": ["capture_evidence", "execute_next", "abort_or_recover"],
  "blocked_ops": [
    {"op": "low_z_move", "reason": "target class is not verified"}
  ],
  "evidence": {
    "required_claims_missing": ["high_z_target_centered"],
    "handles": [
      {
        "kind": "camera_image",
        "path": "data/measurements/images/reg-2026-05-02-001-a1-high-z.jpg"
      }
    ]
  }
}
```

The bridge should return handles, state, allowed operations, and rejection
reasons. It should not dump full command histories into normal agent context.
Full logs belong in evidence files and can be fetched explicitly for debugging.

Evidence artifacts should be returned as handles and compact claim/gate
summaries by default. Full-resolution images, raw command histories, and other
large payloads belong in evidence storage and should be retrieved explicitly
only when an agent needs to inspect them.

## Adapter Roles

### MCP Adapter

Use for LLM agents once the daemon/core can validate plans, manage sessions, and
write evidence. MCP tools should map one-to-one to bridge workflow operations,
not to OT-2 HTTP endpoints.

### Local HTTP Adapter

Use if a future UI, dashboard, or non-MCP agent runtime needs programmatic
access. The HTTP adapter should expose the same session operations as MCP. If a
local HTTP adapter exists, it should normally be the daemon's native API.

### CLI Adapter

Use for operators and development:

- smoke-test robot health,
- inspect artifact identity,
- inspect offset registry,
- manually recover or close a session,
- run CI-style validation without an agent runtime.

The CLI should remain a thin wrapper. It should not become the normal agent
transport for physical motion. For live motion, the CLI should talk to the
daemon rather than creating an independent bridge process.

## Implementation Rule

Build `aevum_ot2.core` first, then the local daemon that owns live sessions. Add
adapters only after the core has stable models, session state, locking,
registry, validation, and evidence writing. Adapter code must not duplicate
validation or robot command logic.
