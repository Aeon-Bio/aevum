# Schema Inventory

## Purpose

This inventory names the persisted or semi-persisted schemas that currently
matter for the OT-2 bridge. It is the owner map for migrations, compatibility
adapters, retention, and fail-closed behavior.

Schema changes must preserve the safety rule:

```text
unknown, ambiguous, stale, or mismatched persisted state cannot authorize motion
```

## Policy

- Every durable JSON or SQLite payload needs an owner module, a schema version
  policy, and tests for compatibility or fail-closed behavior.
- Response-only envelopes can stay unversioned unless they are written to disk
  or used as evidence.
- A migration may preserve no-motion inspection and recovery, but motion gates
  must treat unknown schema versions as blockers until an explicit compatibility
  claim is derived.
- Legacy fields can be read, but they must not satisfy future gates without
  provenance as evidence handles or claims.
- Retention may summarize old session context, but it must not delete evidence
  packets, offsets, command journals, recovery data, or records referenced by an
  active gate or recovery session.

## Migration Rules

1. Additive fields are allowed when defaults preserve no-motion behavior.
2. Renames require a compatibility adapter and a test with a v1 artifact.
3. Enum widening is allowed only when new values are unreachable by existing
   motion paths until transition guards exist.
4. Unknown schema versions must fail with `SchemaVersionError` or a recovery
   scan blocker before the artifact reaches readiness, evidence-claim loading,
   or plan validation.
5. Operation-name migrations must be explicit. Old operation strings may map to
   new no-motion names only through the plan shim layer; raw OT-2 commands,
   arbitrary coordinates, arbitrary Python, and direct offset mutation must
   never be accepted as plan compatibility.
6. The current evidence index is a local trusted writer boundary. Generic
   evidence-event append APIs are acceptable for no-motion commissioning only;
   a future unattended motion backend should move camera capture receipts behind
   a typed, session-bound writer or signed/transactional receipt before treating
   the event log as adversarially tamper-resistant.
